# IROUP Security Readiness
**Last updated: 2026-05-22 | Scope: Student and staff data intake**

This checklist is for the pre-intake security pass before real University of
Phayao student and staff data is added to IROUP V2.

## Immediate Status

- `v2.lookup.students` is admin-only.
- `v2.lookup.staff` is admin-only.
- Real intake files have arrived locally under
  `docs/DATA_MASTER_ Students_Staff/`; this folder is local-only and must not be
  committed to git.
- Mobility and Travel admin pages send V2 admin auth when loading person lookup
  data.
- Mobility and Travel use admin-only server-side person search instead of loading
  the full student/staff sheets into the browser.
- Admin manual-add flows create PERSON_STUDENT/PERSON_STAFF master rows before
  linking participants. Staff IDs are generated by the system; student IDs must
  be supplied from the official student record.
- Public V2 routes must never return row-level student/staff names, IDs, gender,
  participant snapshots, internal notes, budgets, audit fields, or private file
  URLs.

## Before Importing Real Data

- The received `.xls` files do not include a header row; the first row is real
  data. Import scripts must use a fixed source-column mapping and must not treat
  row 1 as headers.
- Confirm and resolve all unit-name mappings before import:
  - student source has 20 distinct unit names; 19 currently match
    `UP_UNIT_MASTER`, with `วิทยาเขตเชียงราย` still unmatched.
  - staff source has 55 distinct unit names; 30 currently match
    `UP_UNIT_MASTER`, with 25 unmatched or historical/closed units.
- Do not import rows with unresolved `unit_id` silently. Either add/approve
  missing units in `UP_UNIT_MASTER` or route them to a reviewed fallback.

- Confirm the source file contains only fields actually needed by IROUP:
  - stable student/staff identifier
  - display name
  - unit/faculty/program or position
  - active/status flag if available
- Do not import unnecessary sensitive fields such as national ID, phone number,
  personal email, address, date of birth, religion, health/disability data, or
  financial information unless a reviewed workflow explicitly requires them.
- Keep the raw import file outside the public website folder and do not commit it
  to git.
- Use sample/test rows for final UI verification before loading real rows.
- Confirm who is allowed to access Admin pages in the V2 `ADMIN` sheet.
- Remove inactive or temporary admin accounts before production use.

## Required Endpoint Checks

- Direct unauthenticated requests must fail:
  - `v2.lookup.students`
  - `v2.lookup.staff`
  - every `v2.admin.*` route
- Direct public requests must pass and remain sanitized:
  - `v2.public.mobility.list`
  - `v2.public.travel.list`
  - `v2.public.mou.list`
  - `v2.public.scholarship.list`
  - `v2.public.event.list`
  - `v2.public.news.list`
  - `v2.public.knowledge.list`
- `v2.schema` and `v2.debug.admintokenmap` are admin-only controlled
  diagnostics. Do not share those URLs publicly.

## UI Checks

- Public pages must show only aggregate or project-level data.
- Public Mobility and Public Travel must not display participant names, person
  IDs, student IDs, staff IDs, row-level gender, or internal participant rows.
- Admin Mobility and Admin Travel may use person lookup only after successful
  admin login.
- Report CSV exports must be considered admin-only data exports.
- Raw CSV export should be reviewed before broad staff use because it can expose
  all fields returned by admin list endpoints.

## File And Drive Checks

- Public files must use `visibility_level = public`.
- Internal/private attachments must use `visibility_level = internal` or a more
  restrictive value.
- Public DTOs must include only public-safe file roles.
- Do not make folders containing raw imports or internal attachments public.

## Operational Rules

- Keep real student/staff data out of screenshots, Git commits, issue comments,
  chat logs, and public demo pages.
- When testing with real records, use the minimum number of rows needed.
- Revoke or rotate admin tokens if a device is lost, shared, or suspected of
  compromise.
- Prefer aggregate counts in dashboard/public surfaces; use row-level identity
  only inside the specific admin workflow that needs it.
